# WaveByte Protocol

## Packet format

All multi-byte integer fields are big-endian.

```
Offset  Size  Field
0       2     MAGIC            0x57 0x42 ("WB")
2       1     VERSION          0x01
3       4     TRANSFER_ID      random per transfer, generated by the sender
7       1     PACKET_TYPE      see Packet Types
8       2     SEQUENCE         packet index within the transfer
10      2     TOTAL            total packet count for this transfer
12      1     PAYLOAD_LEN      0-32
13      N     PAYLOAD          0-32 bytes, N = PAYLOAD_LEN
13+N    4     CRC32            IEEE 802.3 CRC32 of bytes [0, 13+N)
```

### Fixed frame lengths

Every packet is transmitted at one of two fixed lengths, regardless of its actual payload size, so the receiver always knows in advance how many modulation symbols to decode without needing a separate length side-channel:

- **Control frame — 17 bytes** (`HELLO`, `HELLO_ACK`, `ACK`, `ABORT`): header + 0 payload + CRC. These carry no payload and cost the least airtime.
- **Data frame — 49 bytes** (everything else): header + payload zero-padded to 32 bytes + CRC. `PAYLOAD_LEN` in the header still records the *true* payload length; the receiver trims padding after parsing.

This is a deliberate simplification given the modem's low raw symbol rate — see [`architecture.md`](architecture.md) for the reasoning.

## Packet types

| Value | Name | Frame | Payload |
|---|---|---|---|
| 0x01 | HELLO | control | — |
| 0x02 | HELLO_ACK | control | — |
| 0x03 | CAPABILITIES | data | 4 bytes: sender's sample rate (Hz) |
| 0x04 | CAPABILITIES_ACK | data | echoes the sample rate received |
| 0x05 | START_TRANSFER | data | 4 bytes file size, 2 bytes total packets, 1 byte isText flag, 1 byte name length, up to 24 bytes UTF-8 filename |
| 0x06 | DATA | data | up to 32 bytes of file/text content |
| 0x07 | ACK | control | — (meaning depends on context: confirms START_TRANSFER, confirms all DATA received, or confirms hash match) |
| 0x08 | NACK | data | 1 byte count, then up to 15 × 2-byte missing sequence numbers |
| 0x09 | END_TRANSFER | data | 32-byte SHA-256 hash of the complete original data |
| 0x0A | ABORT | control | — |
| 0x0B | TEXT | data | reserved for future direct text framing (current text chat reuses START_TRANSFER/DATA with `isText=1`) |
| 0x0C | CALIBRATE | data | reserved for future peer-assisted calibration |
| 0x0D | CALIBRATE_ACK | data | reserved for future peer-assisted calibration |

## Handshake and transfer sequence

```
SENDER                              RECEIVER
  |--------- HELLO ------------------->|
  |<-------- HELLO_ACK -----------------|
  |--------- CAPABILITIES ------------->|
  |<-------- CAPABILITIES_ACK ----------|
  |--------- START_TRANSFER ----------->|
  |<-------- ACK -----------------------|
  |--------- DATA[0] ------------------>|
  |--------- DATA[1] ------------------>|
  |--------- ...      ----------------->|
  |--------- DATA[N-1] ----------------->|
  |<-------- ACK  (all received)  ------|
  |          or NACK (missing list) ----|
  |--------- DATA[missing...] --------->|   (repeats until ACK or max rounds)
  |--------- END_TRANSFER (hash) ------>|
  |<-------- ACK (hash match)  ---------|
  |          or NACK (hash mismatch) ---|
```

Every step has a timeout and a small retry budget (see `js/file-transfer.js`); if the sender never gets a HELLO_ACK, WaveByte reports a clear failure rather than hanging indefinitely.

## Reliability layers

WaveByte layers three independent forms of error protection, each catching what the layer below it misses:

1. **FEC (Hamming(7,4))** — corrects single-bit errors within each nibble without needing a retransmission at all. Applied to every packet's bytes before modulation.
2. **CRC32 per packet** — after FEC decoding, the receiver recomputes the CRC over the packet body. Any packet that still doesn't check out (multi-bit errors FEC couldn't fix) is treated as not received.
3. **Selective-repeat ARQ (NACK-driven)** — the receiver tracks exactly which sequence numbers it has and asks only for those missing, rather than restarting the whole transfer over one bad packet.
4. **End-to-end SHA-256** — after all packets are individually confirmed, a whole-file hash comparison catches anything the per-packet checks structurally couldn't (e.g., a systematic reassembly bug), and is the final gate before the receiver offers the file for download.

## Transfer IDs

Each transfer gets a random 32-bit `TRANSFER_ID` (via `crypto.getRandomValues`), so stray packets from a previous or abandoned transfer are ignored rather than corrupting a new one.

## Text vs. file transfer

Text messages are sent through the exact same pipeline as files: UTF-8 bytes of the message are treated as file content with `isText=1` in `START_TRANSFER`, so chat messages get the same CRC+FEC+ARQ+SHA-256 reliability as binary file transfers.
